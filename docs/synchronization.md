# 同步机制与延迟排查

## 前台同步

- 网页可见且选中会话：运行／等待中目标每 500ms 发起一次最新页检查；空闲时每 2000ms。上次未完成时等待，不叠加请求；网络失败后退避，最高 10 秒。
- 页面隐藏后暂停轮询；回到前台先更新设备状态，再立即检查当前会话。旧历史分页继续使用独立游标，不能与最新页混用条件缓存。
- 原生会话主要通过本地日志／数据库读取；网页托管的任务仍有实时消息推送。半秒是检查间隔，不代表模型产出或手机接收具有半秒的硬性保证。
- 最新页无变化时使用会话隔离的 ETag 返回 304，不重复下载正文，也不重建消息或图片。切换会话会重置条件缓存。
- 会话元数据通过增量 SSE 更新，避免每次变化都下载全部会话列表；旧网页仍能通过兼容事件刷新。

## 电脑端减负

快速历史请求省去连接层重复的全量同步，不等待 Codex 桌面模型设置读取。设置由后台读取及本地推送更新，轮询的设置读取合并并限频为最多每 10 秒一次。

Windows 原生状态的常规／前台探测改用异步进程，前台 Codex 写入者最多每 2 秒探测一次，同一探测不重叠；结果带版本校验，旧探测不能覆盖新结果。启动首次扫描及明确要求强制核对原生写入者的路径仍保留同步确认，以维持所有权判断。

Claude 的多 MB 日志最新页暂存最多 2 秒，每次仍检查文件大小及修改时间；新追加立即使缓存失效，旧历史页不复用最新页缓存。此短缓存也会定期重新解析图片引用。

只有更新了连接程序的工作电脑才能使用完整轻量路径。旧连接程序仍可服务新版网页，但可能保留原来的扫描／设置读取开销。

## 2026-11-03 实测

本次从 Windows 工作电脑测量，未直接测量用户手机运营商链路，没有向真实 Agent 发送测试任务。

| 项目 | 观察 |
| --- | --- |
| 服务器基础资源 | 约 1.4 GB 内存可用，磁盘使用 36%，未见 CPU 饱和 |
| 服务端回环健康请求 | 约 0.7–0.8 ms |
| 工作电脑到服务器健康请求 | 常见 31–37 ms |

| 本地 Claude 日志 | 16 MB，原最新页纯日志解析约 75–83 ms |

| 隔离网页稳定性 | 未变页走 304；未删除已有消息／图片节点，增量会话事件未额外全量取状态 |
| 更新后快速链路抽样 | Codex 129–192 ms，Claude 90–108 ms |
| 后续 20 次持续抽样 | 中位 304 ms，P95 3754 ms，最长 3794 ms；同期健康请求多数 31–36 ms |

持续抽样仍观察到一段数秒响应，之后回到约 200–300 ms；同期服务器健康接口保持快速，慢点在获取工作电脑数据这一段，尚未完整区分该段内的本机处理、并行同步与通信耗时。检查间隔不能消除冷启动、本机忙碌、共享传输或外网波动。已确认的主要延迟包括实现中的轮询等待、阻塞状态探测和重复读取／传输；没有证据表明应先升级服务器硬件。不能据此排除手机侧网络影响，也不应把全部响应宣称为稳定低于半秒。
