# 同一项目跨电脑接力

服务器保留一个项目和原来的需求 ID。一个项目可以关联多台设备，每台设备登记本机 game 仓库路径；每个需求单独绑定执行设备和独立 worktree。同一项目的不同需求可以留在不同电脑上。

团队配置中的“工作电脑”只设置新需求的默认设备，不会搬迁已有任务或文件。

在需求详情选择 **换电脑接力**，选择在线的新电脑，填写该电脑的 game 仓库绝对路径，点击 **开始接力**。已登记设备的路径会自动带出。服务器和两端 bridge 都需要升级到支持 `studioMigration` 的版本，新电脑需要已经配置团队所用的 Agent。

系统先检查新电脑的路径，然后停止原需求的执行并冻结原副本，保存制作快照，分块传到新电脑，再从指定仓库创建独立分支和 worktree。不会在用户指定的仓库工作目录直接制作，也不覆盖该目录已有修改。

接力完成后：

- 项目、需求、任务、依赖和制作人审批 ID 保持不变。
- 当前需求切换到新电脑；同项目其他需求保留各自的原设备和副本。
- 项目的新需求默认使用接力后的电脑；从旧交付继续制作时，使用该交付实际所在的设备。
- 已完成步骤、批准的视觉方向和已有 QA 结论保留。接力本身不代表新的 QA 或实机验收通过。
- 正在执行的任务在新会话中读取已有成果和原执行上下文，只继续未完成步骤；旧会话保留为历史。
- 已迁移的原画、视频等成果仍可通过原需求查看。

## 保存与传输的数据

worktree 保存制作文件；服务器数据库保存任务调度、审批、会话和设备绑定。完整接力需要两部分，不能把普通 Git 分支当成全部工作室状态。

当前传输使用经过鉴权的 Relay/Bridge 通道和 Git bundle，不需要用户手动提交、推送或配置 GitHub。系统使用临时索引和私有快照引用，不切换源分支，不修改源索引，也不自动推送远端。

快照包括：

- 当前提交历史、已跟踪文件的实际工作版本、普通未跟踪文件。
- 已初始化子模块各自的实际修改和未跟踪文件，恢复成隔离的子 worktree。
- `.studio/` 下的制作资料，以及交付列表中明确引用的被忽略文件。
- 已下载的 LFS 实际文件内容；源电脑只有 LFS 指针时，要求先补齐资源。
- 需求附件、已完成任务、审批记录和原会话的公开执行上下文。

普通忽略缓存不自动复制，`.studio/` 中的依赖缓存也跳过。共享引擎、DCC、Python 环境和 Agent 登录需要在新电脑准备；旧电脑的绝对工具路径不会直接用作新电脑的共享工具配置。

GitHub 可以作为已提交分支的另一个传输渠道；本实现不自动向 GitHub 发布制作文件，也不把 native Agent 会话或登录凭据上传 GitHub。

## 断线和恢复

接力进度会显示在需求详情中，关闭网页不会取消后台传输。分块大小为 256 KiB，保存清单和 SHA-256；失败时保留原现场和已收到的分块，**重试接力** 从确认过的断点继续。服务器重启后会显示可重试状态，不自动重放未确认操作。

当页面显示完整快照已保存到服务器后，恢复该快照不再依赖旧电脑在线。此前旧电脑需要在线。仍有排队输入或未确认投递时，先处理或核对，系统不会丢弃排队消息或重复派发。

目录填错或设备暂时不可用时，可选择 **修改目标电脑 / 路径**。新电脑仓库需要与任务有共同 Git 历史；任务的本地提交通过 bundle 携带，不要求用户先推送这些提交。原副本成功冻结后保持冻结，后续生产使用新副本，避免两台电脑同时写同一个需求。

迁移过程中服务器临时保存快照以便断点续传，完整接力提交成功后删除服务器上的 bundle 包，保留迁移清单和进度记录；不会将成果视频登记为服务器长期媒体。失败时保留临时分块供重试，源电脑与目标电脑本地文件保留。

迁移快照保存在各端数据目录的 `studio-migrations/<迁移 ID>/`，接力 worktree 保存在 bridge 数据目录的 `studio-workspaces/<需求 ID>-migration-<迁移 ID>/`。这两个目录不应当用 GitHub 同步来代替游戏工程版本管理。

## 验证

`test/studio-migration.test.ts` 使用真实临时 Git 仓库验证脏文件、二进制资产、子模块、目标已有修改、分块重试、服务器重启、旧电脑离线恢复和同项目多设备绑定；通过鉴权 HTTP 与真实 Bridge WebSocket 验证完整传输和迁移后的原画读取。开发机测试不等于两台实际生产电脑的验收。
